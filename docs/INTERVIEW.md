## 一、德邦快递小程序（必问，最新经历）

### 1. 简历上说覆盖百度、抖音、快手、H5、高德、鸿蒙多端，这些端的差异具体体现在哪里？你们怎么做的适配？

**参考答案：**

差异主要分三类：

- **API 层**：登录、支付、分享、地图这些能力各端的接口名和入参都不一样。我们的做法是收口到统一的 `adapter` 层，按端实现各自 provider，业务代码只调统一接口，编译期按平台打包对应实现。
- **渲染层**：同一个 CSS 在不同端表现不一致。比如抖音端对 `overflow: hidden`、fixed 定位的处理和微信不同，安全区（底部 Home 条、刘海屏）各端取值方式也不同，我们封装了 DPSafeArea 组件统一处理。
- **组件/语法支持度**：uni-app 编译到非微信端时，部分 Vue 特性和组件支持不完整（比如 provide/inject 在抖音端通讯失效），这类问题要在技术选型和组件设计阶段就规避，用 props 透传、全局状态或事件总线替代。

适配的总原则是：**差异收敛在适配层和基础组件层，业务层代码保持一套**。

### 2. 你提到解决了"抖音端页面无法滚动"的问题，具体是怎么定位和解决的？

**参考答案：**

现象是页面在微信端正常，抖音真机上滑不动。定位过程：先用抖音开发者工具真机调试，检查页面 DOM 结构，发现页面根容器被外层组件设置了 `overflow: hidden` 加固定高度——微信端 page 级滚动不受影响，但抖音端的渲染层对 page 滚动的处理不同，容器高度把内容截断了。

解决方案有两个方向：一是去掉容器的高度限制，让内容自然撑开走 page 级滚动；二是对于必须固定布局的页面（比如列表页），改用 `scroll-view` 包裹内容，滚动交给组件内部处理。我们后来沉淀成规范：长列表页面统一用 DPInfiniteLoading 封装 scroll-view 的滚动加载，避免各端再踩这个坑。

### 3. provide/inject 在抖音端失效，原因是什么？

**参考答案：**

小程序端 uni-app 是把 Vue 组件树映射成原生自定义组件来运行的，provide/inject 依赖的是 Vue 运行时的组件链路。微信端的运行时模拟得比较完整，而抖音端自定义组件的实例关系和组件链路跟 Vue 的对应关系有差异，导致依赖收集和注入失败。

这属于"编译型多端框架的原生差异"，解决思路不是修它，而是绕开：跨层级通讯改用全局状态管理（store），或者用 `uni.$emit / uni.$on` 事件总线。我们把它写进了开发规范的"多端禁用清单"里，code review 时会卡。

### 4. 新版百度小程序全量替换旧版，怎么做到"用户无感升级"的？

**参考答案：**

无感升级的核心是**旧路径全部要有承接**。做了几件事：

1. **路由映射**：先梳理旧版全部页面路径和入口（分享卡片、二维码 scene、搜索直达、外部 H5 跳转），新版本上线的路径与旧版保持一致，无法一致的路径做中转页 redirect。
2. **参数兼容**：旧版分享出去的链接带的 query 和 scene 参数，新版入口页统一解析后转发到对应页面，保证老分享卡片永远能打开。
3. **灰度发布**：百度小程序支持按比例放量，我们先小流量验证，观察埋点和错误上报，再逐步到全量。
4. **回滚预案**：旧版本包保留可随时回退，上线前把回滚流程演练过一遍。

最终功能覆盖率 90%、核心流程回归通过率 100%，没覆盖的 10% 是低频功能，用保留旧路径或 H5 兜底承接。

### 5. "功能覆盖率 90%、回归通过率 100%"这两个数字是怎么统计出来的？

**参考答案：**

功能覆盖率是对旧版本做**页面 × 接口 × 埋点**三个维度的清单化盘点：把旧版所有页面路由、每个页面调用的接口、关键交互的埋点事件列成表，逐项在新版里找到对应实现就算覆盖，最后覆盖项/总项就是覆盖率。剩下 10% 是低频功能（比如已下线业务的入口），产品确认后走兜底方案。

回归通过率是对核心流程（下单、查件、支付、客服这些）建回归 checklist，用小程序自动化测试工具跑关键路径用例，加上人工回归，通过的用例数/总用例数。上线后用错误上报和核心埋点对比做二次验证。

### 6. "零回滚、零 P0/P1 故障"，你在质量保障上具体做了什么？

**参考答案：**

事前、事中、事后三段：

- **事前**：需求阶段做复杂度评估和任务拆解，识别高风险点；开发时对修改的模块补单元测试；提测前先自测核心流程。
- **事中**：灰度发布，分批放量，实时盯错误上报和核心指标（下单转化、接口成功率）。
- **事后**：建立线上问题响应机制，明确什么级别的问题走什么流程。

另外规范本身也是质量手段——目录结构、命名、组件设计统一之后，新代码出问题的概率明显下降。

### 7. DPTabs、DPSafeArea、DPInfiniteLoading 这些组件是怎么设计的？

**参考答案：**

这三个组件都是多端踩坑之后沉淀的，设计原则是"把端差异吃在组件内部，对外暴露统一 API"：

- **DPTabs**：标签页组件。各端 tab 的滚动吸顶、下划线动画实现差异大，组件内部按端适配，对外只暴露 tabs 数据和 change 事件。
- **DPSafeArea**：安全区适配。统一处理底部 Home 指示条、刘海屏顶部的高度，对外暴露 slot 和占位开关，业务方不用关心当前端的取值方式。
- **DPInfiniteLoading**：滚动加载列表。内部封装 scroll-view 的滚动监听、触底加载、加载态/空态/错误态，对外只传请求函数。这个组件同时也是对第三方 paging 插件的替代——那个插件在部分端有列表加载异常弹窗的问题。

### 8. 你牵头制定的前端开发规范包含什么？怎么落地的？

**参考答案：**

规范覆盖四块：目录结构（页面、组件、适配层、工具函数的位置约定）、命名约定（文件、组件、变量、接口请求的命名）、组件设计（什么粒度抽组件、props 怎么设计、多端禁用清单）、以及提测上线流程。

落地比制定更重要，我的做法是三件事：一是配套 CLI/模板，新页面新组件按模板生成，规范"长在工具里"而不是文档里；二是 code review 按规范清单卡点；三是拿历史模块开刀——重构了接口请求、客服入口这些实现不佳的模块作为示范，可读性提升约 50%，大家看到收益之后执行就顺了。

### 9. "代码可读性提升 50%"这种主观指标怎么衡量？

**参考答案：**

坦白说可读性没有绝对精确的度量，我用的是可量化的代理指标：重构前后对比同功能模块的代码行数、重复代码率（用工具扫描）、以及团队理解一个模块所需的平均时间（用新同学上手成本和 review 轮次来观察）。50% 是综合代码量和重复率下降得出的估算，面试时我也会如实说明这是估算值，核心证据是重构后同类需求改动耗时明显下降。

## 二、淘米旗下项目

### 10. 会员中心小程序从 0 到 1，你当初怎么搭的架构？

**参考答案：**

先定分层：页面层、业务组件层、基础组件层、服务层（API 封装）、工具层。几件关键决策：

- **API 层统一封装**：请求拦截、登录态注入、错误码统一处理、loading 管理，业务侧只写接口定义和回调。
- **弹窗 API 化**：把常用弹窗封装成 API 调用形式（类似 wx.showModal 的体验），业务代码从"写结构"变成"调函数"，这块减少了约 20% 开发工作量。
- **组件资产化**：登录、分享图生成、雪碧图合成等做成可复用组件，最终沉淀 40+ 组件支撑 20+ 页面。

### 11. 客服平台重构，你怎么做到减少 50% 重复代码的？

**参考答案：**

先做问题盘点：老代码里表格、弹窗、表单校验、权限控制全是各页面各写一套。重构时逐类收口：

- **kf-table**：把表格的列配置、分页、加载态、操作栏收进配置化组件，一个表格页面从上百行模板变成一份列配置。
- **kf-dialog**：弹窗的开关状态、按钮组、异步确认逻辑统一封装。
- **v-auth**：权限指令化，按钮级权限一行指令搞定。
- **api.js**：请求模块统一错误处理和数据转换。

50% 是重构前后同功能页面代码量的对比。更重要的是后续新需求的开发方式从"复制粘贴改"变成"写配置"。

### 12. 低代码平台怎么设计的？为什么能减少 80% 重复工作？

**参考答案：**

架构是 **Schema 驱动 + 物料体系**：

- 上层是可视化编辑器，产出页面 JSON Schema；
- 中间是渲染引擎，按 Schema 动态渲染页面，走运行时渲染而不是出码，改配置即时生效；
- 底层是物料组件库，表单项、列表、弹窗这些高频模式做成物料，注册进物料中心。

减少 80% 的原因：这类活动/表单类页面 80% 的工作是重复的表单、列表、弹窗组合，平台把这些变成了配置。目前已支撑 3 个项目。同时我会强调边界——复杂交互页面我们仍然走代码开发，平台只接管模式化页面。

### 13. qiankun 微前端遇到过什么问题？怎么解决样式冲突和主题同步？

**参考答案：**

- **样式冲突**：qiankun 的沙箱对样式隔离不彻底。解决是子应用内部全量 scoped + 通用样式加应用前缀，配合 qiankun 的样式隔离配置；公共依赖（如 UI 库）不重复引入。
- **主题同步**：主应用把主题变量（品牌色等）通过 CSS Variables 挂在根节点，子应用全部用变量取色；切换主题时主应用修改变量，子应用自动生效，另外通过 props 把用户态传给子应用做初始化。
- **选 qiankun 的原因**：当时需要把新平台和老系统整合、独立开发部署，qiankun 对路由和 JS 沙箱的支持最成熟，接入成本最低。

## 三、阅流播放器

### 14. 播放器技术选型你是怎么做决策的？

**参考答案：**

先明确约束：要支持 MP4 点播、m3u8 直播/点播、flv 直播，要在 PC、H5、小程序多端用，还要被多个项目复用。对比了 video.js（生态全但体积大、定制成本高）、hls.js/flv.js（只管协议不管 UI 和业务）之后，决策是**不整包依赖某一库，而是分层**：协议层用 hls.js + flv.js + 原生 video 各做 adapter，上层自己封装统一的 MediaPlayer 接口（play/seek/截图/倍速等），UI 和业务组件建在接口之上。这样任何一个协议库可以替换，业务层零改动。

### 15. 直播 300ms 低延迟是怎么实现的？

**参考答案：**

分两层讲，先说清各自贡献：

**底层（服务能力）**：低延迟直播服务用 RTC 类协议——UDP 传输、服务端就近分发、不做长缓冲，基础延迟天然比 HLS/FLV 拉流低一个量级（HLS 的切片机制决定了秒级延迟）。

**播放器侧（我做的）**：一是把直播能力集成进自研播放器封装，在统一的 MediaPlayer 接口下新增直播 adapter，处理事件协议、状态同步、断流重连；二是低延迟优化——实时监控 buffered ahead，超过阈值就 seek 到最新位置做**追帧**，防止延迟累积；起播只缓冲必要量；在卡顿和延迟之间按实时审片"延迟优先"调平衡。

300ms 是服务基础延迟 + 播放器侧防累积的端到端结果。这样答既不冒领服务的工作，也把自己真实的优化点讲透了。

### 16. 30+ 播放器组件怎么划分的？组件化带来什么？

**参考答案：**

分三类：**接口组件**（对接数据，如播放列表、权限）、**容器组件**（控制播放器生命周期和布局）、**功能组件**（进度条、多屏、标注、截图、缩放预览等）。分类标准是"职责单一 + 依赖方向单一"，功能组件只依赖 MediaPlayer 接口不依赖业务。

收益是开发效率提升约 50%：新场景（比如多屏播放器支持 2~4 路同播）变成了功能组件的组合。另外通过 submodule 把播放器抽成独立模块，3+ 项目、14+ 同事在用，后来具备了单独发 npm 包的条件。

### 17. 视频圈点标注是怎么实现的？

**参考答案：**

在 fabricjs 基础上封装了一套绘图工具组件：以视频画面为画布底，支持圈、点、线、文字标注，标注数据（含时间点）序列化存储，回放时按时间轴渲染。难点主要是三件事：画布坐标和视频原始分辨率的换算（保证标注在不同尺寸屏幕上位置一致）、标注随播放进度显隐、以及撤销重做。没有直接用 fabricjs 原生工具栏，而是按业务交互重新封装了整套 API。

## 四、通用技术题（简历技术栈必考）

### 18. Vue3 Composition API 相比 Options API 的实际收益？（你有 10+ 个 Hooks 的实践）

**参考答案：**

最大收益是**逻辑复用**。Options API 时代复用逻辑靠 mixin，命名冲突和来源不透明是硬伤。我在智慧美育项目里把文件上传、表格列表+分页、表单校验这些高频逻辑抽成 useUpload、useTable 等 10+ 个 Hooks，页面里一个 Hook 顶原来一大段 data/methods/watch，整体减少约 50% 代码量。其次是**逻辑按功能聚合**而不是按选项类型分散，长组件的可读性明显变好；配合 TypeScript 的类型推导也更好。

### 19. 小程序登录流程？多端登录怎么统一？

**参考答案：**

标准流程：前端调 `uni.login` 拿 code → 后端拿 code 去微信（或对应平台）服务端换 openid/session_key → 后端签发自己的 token → 前端存 storage，后续请求带头。多端的差异在第一步各端的 provider 和换取逻辑不同，收口在登录 adapter 里：对外统一 `login()` 接口，按端走各平台实现，token 之后的体系完全一致。手机号绑定、静默登录失败降级这些也统一在 adapter 层处理。

### 20. 小程序双线程模型是什么？它导致过你什么实际问题？

**参考答案：**

小程序是渲染层（WebView）和逻辑层（JS）分离的双线程架构，两边通过 Native 层异步通讯。实际影响过的点：setData 频繁调用或传大数据导致通讯开销大、页面卡顿——优化方向是合并更新、只传变化字段、长列表走虚拟列表；还有节点查询（createSelectorQuery）是异步的，某些和渲染时序相关的逻辑要处理好时序问题。

### 21. TypeScript 在项目里怎么用的？收益在哪？

**参考答案：**

从接口层入手收益最大：请求函数的入参、返回值全部定义类型，后端字段改名在编译期就报错。再往外推到组件 props、store 状态、公共工具函数。Vue3 + TS 的组合下 defineProps 的类型推导、Hooks 的泛型封装都很顺。收益是重构和多人协作时的安全感——我在客服平台和会员中心都是这个打法。

### 22. 你搭过 CLI 工具（tm-cli），解决了什么问题？

**参考答案：**

痛点是活动类项目重复搭建：目录、构建配置、公共库引用每次都手动复制。tm-cli 做了三件事：项目模板初始化（交互式选择活动类型）、组件/页面代码生成（按模板产出文件并自动注册）、以及内置构建配置。节省约 20% 初始化和样板代码时间，也让不同人创建的项目结构天然一致。

## 五、AI 研发效率（简历亮点，大概率被追问）

### 23. Claude Code、Codex、ZCode、Trae 这些工具你都怎么用？怎么选？

**参考答案：**

我把它们分成两类用：

- **Agent 型**（Claude Code、Codex、ZCode）：适合中大任务——多文件重构、新功能开发、排查问题。我会先写好项目上下文约定（AGENTS.md/CLAUDE.md 这类），让 agent 理解项目规范再动手。
- **IDE 辅助型**（Trae、Copilot 这类）：适合小步快跑——补函数、写单测、改样式。

选型原则：任务越需要跨文件理解和自主执行，越用 Agent 型；越局部、越确定，用补全型越快。关键不是记住哪个工具，而是把"需求拆解 → 上下文准备 → 验收标准"这套和 AI 协作的方法练熟，工具换了方法不变。

### 24. "多 Agent 协作"具体指什么？你在团队怎么落地的？

**参考答案：**

单个 Agent 一次做完大任务容易跑偏，多 Agent 的思路是像带团队一样分工：**规划 Agent** 负责拆任务和定方案，**实现 Agent** 并行做各个子任务，**审查 Agent** 负责代码 review 和测试校验，人负责定验收标准和最终合并。我在德邦做过多 Agent 提升研发效率的技术分享并在小组推广，实际用在批量重构（比如规范落地时批量改接口调用）和回归测试用例生成这类可并行、可验证的任务上，效率提升约 50%。核心经验是：**任务越可验证（有测试、有明确验收），Agent 交付质量越高**。

### 25. 什么是 VibeCoding？会不会导致代码质量下降？

**参考答案：**

VibeCoding 我的理解是"人负责意图和验收，AI 负责实现"的开发模式：人把需求、约束、上下文描述清楚，AI 生成实现，人通过 review 和测试把关。质量下降的风险真实存在，我的应对是三条：一是规范前置，把编码规范写进 AI 的上下文约定里；二是测试兜底，AI 写的代码必须过单测和回归；三是关键模块（支付、登录这类）AI 产出后人工逐行 review。用这套方法提效的同时，德邦上线零 P0/P1 也是质量没掉队的证据。

### 30. 德邦小程序量级那么大，微信端也是你负责的吗？

**参考答案：**

不是。德邦小程序的微信、支付宝端由独立团队维护（另一套技术栈）；其余端（百度、抖音、快手、高德、鸿蒙、H5）基于 uni-app 新技术架构统一开发，这是我负责的部分。这套多端架构的出发点正是解决长尾端逐个开发的成本问题——我先在新版百度端完成新旧架构的全量替换，再把这套架构复用到抖音、快手端的开发上线，这也是简历里"多端开发成本降低 40%"的由来。

### 31. "年触达千万级用户"这个数字是什么口径？

**参考答案：**

口径是寄件人和收件查件用户按年去重，含微信主端在内的全部端，我负责的多端矩阵承接的正是 C 端散客的线上寄递场景。推算链是：小程序日均下单 40 万+，年下单超 1.4 亿；散客寄件年均 1~3 单，仅寄件人年去重就达千万级，加上每单触达的收件查件用户，"年触达千万级"是保守表述。需要主动说明的是：这是"年触达"不是月活——月活是百万级量级（日均下单 40 万，含查件用户月活在数百万级）。

### 32. 为什么微信端不也用 uni-app 统一，而要维持双架构？

**参考答案：**

微信、支付宝端历史包袱重，其中微信端承载最大流量，稳定性优先，整体重写迁移的风险和收益不成比例；而长尾端页面规模小、迭代快，一套代码覆盖多端的收益最大。所以公司采用"主端原生稳态 + 长尾端跨端框架"的双架构策略，这也是行业里多端业务的常见做法。
